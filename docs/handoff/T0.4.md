# T0.4 Protocol fixes, data part (holiday day type, 1-18 table set) · data

Status: done (data part). The eval part (GTFS baseline, blend column) and the ml part (BLEND_S) belong to those agents.

## What changed
- `model/scripts/aggregate.py`: new env var `HOLIDAYS` (comma list of October days). Those days are pooled with weekends:
  the daytype label is "weekend", so `ttmodel.py` and every 2-daytype consumer read the tables unchanged.
  If unset, behaviour is v1 (calendar weekday/weekend). `stats.json` records `holidays_pooled_with_weekend`.
- `model/scripts/run_tables.py` (new): builds both table sets with `HOLIDAYS=02,20`.
- Outputs: `E:\hackathon-work\v2\data\tables_1_18\` (validation-time selection) and `tables_1_24\` (serving), each
  with segment_times.csv, stop_headways.csv and stats.json. The v1 tables in E:\hackathon-project\model are untouched.

## Flag
`HOLIDAYS` (build time). To serve the v2 tables, point `MODEL_DIR` at a folder containing tables_1_24's CSVs.
v1 stays the default.

## How to run
`python E:\hackathon-work\launch.py <log> E:\hackathon-wt\data\model\scripts\run_tables.py` (about 3 min for both)

## Validation / evidence
- tables_1_24: 35.35 M passings, 90.5% segment coverage, 2,203 routes covered (same as v1).
  tables_1_18: 26.29 M passings, 89.3% segment coverage, 2,154 routes.
- Network speed by day from map-matched segments, 08-20 IST, in km/h (descriptive only):
  2 Oct (Fri, Gandhi Jayanti) 20.5; 20 Oct (Tue, Dussehra) 19.8; Sundays 4/11/18/25: 19.2/18.8/18.4/17.6;
  Saturdays 3/10/17/24/31: 16.8/17.1/16.1/15.9/15.3; typical weekdays 15.5-16.2.
  Both holidays run like (or faster than) Sundays, which supports pooling them with weekends.

## Open issues (for humans / eval)
- **Saturdays look like weekdays** (15.3-17.1 km/h vs Sundays 17.6-19.2). Pooling Saturday with Sunday may bias
  weekend tables. A 3-class day type (weekday / Saturday / Sunday+holiday) would need ttmodel's [.., 2, 24] arrays
  widened to 3. Not done.
- Other possible holidays: 26 Oct (Mon; possibly Maharishi Valmiki Jayanti, which I have not confirmed as
  gazetted in Delhi for 2026) at 16.8 km/h, and 19 Oct (Mon, the eve of Dussehra) and 29 Oct (Thu) at 17.5-17.6 km/h.
  Speeds are a little high but not holiday-level. 26 and 29 are test days, so I left them as weekdays. Humans should
  confirm the gazetted list.

# T0.4 Protocol fixes, eval part (GTFS baseline on the 600k rides, blend column) -- done

## What changed
- `eval/ride_baselines.py --set test|val`: ride-level error table per model x ride-length bucket x peak, with n in
  every row. Models: `gtfs` (GTFS scheduled board->alight time on the same route pattern, planner network
  `sched_seg` by trip-start hour, hour = ride start hour; pure schedule, no hour factor), `sum_median`, `sum_mean`,
  `blend` (median for the first 600 s then mean, = planner SEG_MODE=blend), `xgb` (final XGBoost, test only) and the
  v1 band (p50 = blend, p85 = sum of segment p85s).
- `eval/val_blend.py`: the validation rides (fold4.parquet) had no blend sum; this rebuilds the 1-18 lookup exactly
  as build_rides.py and writes `E:\hackathon-work\v2\eval\val_blend.parquet` (check: reproduces fold4 base_med with
  0.0 median relative difference, 0% of rides > 1% off). Takes 30 s. `--blend-s 300 450 600 900 1200` gives the ml
  agent's BLEND_S grid on val in one run.
- Outputs: `E:\hackathon-work\v2\eval\rides_{val,test}_metrics.csv`, `rides_{val,test}_summary.md`.

## Flag
None (measurement of v1).

## How to run
    python eval\val_blend.py                 (once, for the val blend column)
    python eval\ride_baselines.py --set val
    python eval\ride_baselines.py --set test (v1 measurement on the existing 600k rides, allowed by the card)

## Results: median APE (within +-20%)
Validation, fold-4 rides days 19-24, 1-18 tables, n = 300,000 (151,518 / 98,372 / 38,942 / 11,168 per bucket):

| Model | <10 | 10-30 | 30-60 | >60 | All |

| GTFS schedule | 31.65% | 24.58% | 23.09% | 26.96% | 27.53% (38%) |
| Sum of medians | 13.66% | 11.82% | 13.16% | 16.59% | 13.05% (66%) |
| Sum of means | 16.57% | 13.18% | 13.09% | 13.75% | 14.77% (62%) |
| Blend 600 s | 13.66% | 12.50% | 13.12% | 14.07% | 13.21% (66%) |

Test (existing 600k held-out rides, days 25-31, 1-24 tables; v1 measurement), n = 600,000
(302,145 / 195,063 / 79,283 / 23,509):

| Model | <10 | 10-30 | 30-60 | >60 | All |
|---|---|---|---|---|---|
| GTFS schedule | 31.74% | 25.10% | 23.55% | 27.63% | 27.92% (37%) |
| Sum of medians | 13.18% | 11.36% | 12.97% | 18.33% | 12.69% (68%) |
| Sum of means | 15.71% | 11.81% | 11.40% | 13.36% | 13.58% (65%) |
| Blend 600 s | 13.18% | 11.61% | 11.68% | 13.92% | 12.46% (68%) |
| XGBoost final | 13.39% | 11.02% | 11.23% | 13.99% | 12.28% (69%) |

- The XGBoost and blend test numbers reproduce the v1 report (12.28% / 12.45-12.46%), which checks the pipeline.
- The GTFS baseline on the 600k rides is **27.9%**, not the 32.5% in the v1 report (that was schedule x prior hour
  factor on 20k rides). Report/T5.1 should use 27.9% with this definition, or state both.
- On val, blend 600 s is *worse* overall than the sum of medians (13.21% vs 13.05%); it only wins on >60 min rides.
  Relevant for the ml agent's BLEND_S choice (T0.4 ml part).
- v1 ride band (blend, sum of p85s) on val: coverage 87.3 / 86.2 / 83.6 / 75.9% by bucket (86.0% overall),
  width 30%, under-p50 49%. Long rides are under-covered.
