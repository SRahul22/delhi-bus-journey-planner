# T2.2 Pooled parallel routes (planner)

Status: implemented behind `V2_WAIT=pooled` and validated on 19-24 Oct (waits only). Gate decisions are for humans.

## What changed
- For every bus leg (board stop s0 -> alight stop s1 on route r) the planner builds the **attractive set**: every route pattern that serves s0 then s1 in order and whose ride time (v1 tables, same departure) is <= 1.1 x the best one. r is always in the set.
- The leg's wait becomes the **pooled wait**: expected wait for a random arrival in the query hour at s0 for the first bus of *any* route in the set, from the gaps between consecutive observed buses (days 1-24, same day type; holidays 2 and 20 Oct count as weekend). It is computed exactly over the hour (each gap weighted by its overlap with the hour, wait capped at 1,200 s; arrivals after the day's last bus are left out). It is used when there are >= 20 gaps; otherwise the v1 wait is kept.
- Cache per (stop, route set, hour, day type), in memory, thread-safe.
- Leg fields added in pooled mode: `wait_source` (pooled or v1), `wait_v1_s`, `pooled_n_gaps`, `pooled_n_days`, and `alternatives` = the rest of the set as [{route, route_id, ride_s}] (the card's "return the set as alternatives"). The v1 `alt_routes` field is unchanged.
- RAPTOR itself still uses v1 waits to search; pooled waits apply when each candidate journey is timed (time_journey), so they change the reported times and the ranking, not the search. This keeps latency flat.

## Data source (A1 caveat)
- Index file: `POOLED_INDEX` (default `E:\hackathon-work\v2\planner\pooled_index_1-24.npz`), built by `planner\build_pooled_index.py`. Format: see E:\hackathon-work\v2\planner\README.txt.
- Two index sources exist: v1 map-matched passings (pass_DD.npz, ~68% of trips, so waits are biased up), `pooled_index_1-24.npz` / `_1-18.npz`; and data's raw stop visits (A1), `pooled_index_visits_1-24.npz` / `_1-18.npz` (built 19:59 once stop_visits 1-24 landed). The code default is still the pass-based file; switching the default to the visits file was pending the visits-based validation run (see below).
- data's `stop_headways_v2.csv` is not used: it is per (stop, route), and pooling needs the bus times of several routes merged.

## Flag
`V2_WAIT=pooled` (default v1). `V2_WAIT=gaps` belongs to data (ttmodel.py) and is not affected.

## Files

## Validation (19-24 Oct only)
400 random ODs (seed 2026, stops 2-20 km apart, departures 06:00-22:00, days 19, 21, 22, 23, 24), first bus leg of the recommended option. Prediction index from days 1-18 (pass-based); realized wait from data's stop visits on the same day (first bus after arriving at the stop). Legs with no realized bus within 60 min excluded (98 of 400). Output: E:\hackathon-work\v2\planner\pooled_validation.csv.
- 73.5% of legs got a pooled estimate (rest fall back to v1); 41.8% had more than one route in the attractive set.
- Against the realized wait for any route in the set (n=302): v1 bias mean -556 s / median -282 s, MAE 703 s, median AE 413 s; pooled bias mean -364 s / median -120 s, MAE 642 s, median AE 392 s.
- Legs with a set of 2+ routes (n=144): v1 median bias -222 s, MAE 560 s; pooled median bias -98 s, MAE 508 s.
- Against the planned route only (n=281): v1 median bias -415 s, MAE 782 s.
- Both still under-predict waits by a lot (G2 asks +-60 s): realized waits in this sample are long (mean 2,323 s for any route in the set, including waits over 60 min). Part of that is the truth source (a route with few GPS-visible buses that day) and part is real.
